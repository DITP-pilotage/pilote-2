# 003. Implémentation d'un système d'historique d'événements pour les indicateurs

## Statut

**Proposé** - En attente de validation et d'implémentation

## Contexte

### Situation actuelle

L'application pilote-2 gère actuellement les valeurs d'indicateurs avec une approche limitée :

1. **Stockage des valeurs** : Les valeurs réelles (`valeur_initiale` et les jalons dans `indicateur_territoire_jalon`) sont stockées directement dans les tables, tandis que les valeurs calculées (*_mandat) sont dérivées
2. **Système de proposition** : Une table `proposition_valeur_actuelle` permet de proposer de nouvelles valeurs, mais avec des limitations :
   - Seule la dernière proposition est conservée (via `annulePropositionValeurActuellePrecedente`)
   - Pas d'historique des changements de statut
   - Pas de traçabilité complète des modifications

**Important** : Les champs se terminant par `*_mandat` sont des valeurs calculées et ne doivent pas être historisées. Seules les valeurs "source" doivent être trackées.

### Problèmes identifiés

1. **Perte d'historique** : Les anciennes propositions sont supprimées, rendant impossible l'audit des modifications
2. **Traçabilité limitée** : Impossible de suivre l'évolution des valeurs dans le temps
3. **Gestion des jalons complexe** : Le système de jalons (`indicateur_territoire_jalon`) est déconnecté du système de propositions
4. **Manque de contexte** : Les raisons des changements et l'historique des décisions sont perdues

## Décision

Nous décidons d'implémenter un système d'historique d'événements basé sur une nouvelle table `IndicateurValeurEvenement` qui centralisera tous les événements liés aux valeurs d'indicateurs.

### Architecture proposée

```sql
model indicateur_valeur_evenement {
  id                    String               @id @default(dbgenerated("gen_random_uuid()")) @db.Uuid
  
  // Identification
  indic_id             String
  territoire_code      String
  jalon                Int?                 // Null pour les valeurs principales
  
  // Type d'événement
  type_evenement       type_evenement       // CREATION, MODIFICATION, PROPOSITION, VALIDATION, ANNULATION
  type_valeur          type_valeur          // VALEUR_ACTUELLE, VALEUR_CIBLE, VALEUR_INITIALE
  
  // Valeurs
  valeur_precedente    Float?
  valeur_nouvelle      Float?
  date_valeur          DateTime?            @db.Date
  
  // Métadonnées
  date_evenement       DateTime             @default(now()) @db.Timestamp
  auteur_id            String               @db.Uuid
  motif                String?
  source_donnee        String?
  methode_calcul       String?
  
  // Contexte
  contexte_import      Json?                // Informations d'import si applicable
  proposition_id       String?              @db.Uuid // Référence à la proposition associée
  
  // Relations
  indicateur_territoire indicateur_territoire @relation(fields: [indic_id, territoire_code], references: [id, territoire_code], onDelete: Cascade)
  auteur               utilisateur           @relation(fields: [auteur_id], references: [id], onDelete: Cascade)
  
  @@index([indic_id, territoire_code, date_evenement])
  @@index([auteur_id])
  @@index([type_evenement])
  @@schema("public")
}

enum type_evenement {
  VALEUR_CREE
  VALEUR_MODIFIEE
  VALEUR_HISTORISEE
  PROPOSITION_VALEUR_CREE
  PROPOSITION_VALEUR_MODIFIEE
  PROPOSITION_VALEUR_SUPPRIMEE
  PROPOSITION_VALEUR_REFUSEE
  PROPOSITION_VALEUR_ACCUSEE_RECEPTION
  PROPOSITION_VALEUR_ACCEPTEE
  PROPOSITION_VALEUR_IGNOREE_VALEUR_MODIFIEE
  PROPOSITION_VALEUR_IGNOREE_VALEUR_HISTORISEE
  PROPOSITION_VALEUR_ACCEPTEE_AVEC_MODIFICATION
  @@schema("public")
}

enum type_valeur {
  VALEUR_AVANCEMENT
  VALEUR_CIBLE
  VALEUR_INITIALE
  
  @@schema("public")
}
```

### Cycle de vie d'une valeur (VA/VC/VI) d'indicateur - 12 étapes clés
*Basé sur le workflow des Propositions de Valeurs Actuelles (PVA)*

#### **Étape 1 - Création de la VA**
**Description** : Création initiale de la valeur actuelle de l'indicateur
**Événements possibles** : `VALEUR_CREE`
**Déclencheurs** : Initialisation d'un nouvel indicateur ou première saisie manuelle
**Détail** : Une valeur d'un indicateur a été ajouté via un import

#### **Étape 2 - Proposer une nouvelle valeur**
**Description** : Le territoire propose une nouvelle valeur actuelle
**Événements possibles** : `PROPOSITION_VALEUR_EN_COURS`
**Déclencheurs** : Action du territoire via l'interface utilisateur
**Détail** : Une proposition de valeur à été effectué par un utilisateur autorisé

#### **Étape 3 - Modifier une proposition existante**
**Description** : Le territoire modifie sa proposition en cours
**Événements possibles** : `PROPOSITION_VALEUR_MODIFIEE`
**Déclencheurs** : Modification d'une proposition existante par le territoire
**Détail** : Un utilisateur effectue une modification d'une proposition de valeur, on ajoute un évenement de `PROPOSITION_VALEUR_MODIFIEE` pour la nouvelle valeur.

#### **Étape 4 - Supprimer une proposition de valeur**
**Description** : Le territoire retire sa proposition
**Événements possibles** : `PROPOSITION_VALEUR_SUPPRIMEE`
**Déclencheurs** : Action "supprimer" du territoire sur sa proposition
**Détail** : L'utilisateur décide par interface sur supprimer la proposition de valeur, on ajoute un évenement de `PROPOSITION_VALEUR_SUPPRIMEE` pour la nouvelle valeur.

#### **Étape 5 - Accuser réception**
**Description** : La direction de projet prend connaissance de la proposition
**Événements possibles** : `PROPOSITION_VALEUR_ACCUSEE_RECEPTION`
**Déclencheurs** : Direction consulte/marque comme "lu" la proposition
**Détail** : L'utilisateur valide la consultation de la proposition, on ajoute un évenement de `PROPOSITION_VALEUR_ACCUSEE_RECEPTION` pour la proposition de valeur. Suite à cela, plus aucune modification ne peut être effectuée sur la proposition de valeur.

#### **Étape 6 - Refuser la proposition**
**Description** : La direction refuse la proposition, retour à la valeur initiale
**Événements possibles** : `PROPOSITION_VALEUR_REFUSEE`
**Déclencheurs** : Décision de refus par la direction de projet
**Détail** : L'utilisateur refuse la proposition via l'interface, on ajoute un évenement de `PROPOSITION_VALEUR_REFUSEE` pour la proposition de valeur. On considère que la proposition est terminée, on pourra constater la date de refus dans la box indicateur et dans l'historique des événements.

#### **Étape 7 - Accepter la proposition**
**Description** : La direction accepte la proposition telle quelle
**Événements possibles** : `VALEUR_MODIFIEE`, `PROPOSITION_VALEUR_ACCEPTEE` (nouvelle valeur = valeur proposée)
**Déclencheurs** : Décision d'acceptation par la direction de projet
**Détail** : L'utilisateur accepte la proposition telle qu'elle est, on ajoute un évenement pour la proposition de valeur, puis on met un nouvel évenement de modification qui lui permet de tracer la nouvel valeur de l'indicateur

#### **Étape 8 - Accepter avec modification**
**Description** : La direction accepte le principe mais modifie la valeur
**Événements possibles** : `VALEUR_MODIFIEE`, `PROPOSITION_VALEUR_ACCEPTEE_AVEC_MODIFICATION` (nouvelle valeur ≠ valeur proposée)
**Déclencheurs** : Acceptation avec ajustement par la direction de projet
 L'utilisateur accepte la proposition mais effectue une modification de la valeur, on ajoute un évenement pour la proposition de valeur, puis on met un nouvel évenement de modification qui lui permet de tracer la nouvel valeur de l'indicateur

#### **Étape 9 - Import sur proposition - même date de VA**
**Description** : Import automatique de données avec date identique à la proposition et valeur de la proposition différente de la valeur existante
**Événements possibles** : `PROPOSITION_VALEUR_IGNOREE_VALEUR_MODIFIEE`, `VALEUR_MODIFIEE`
**Déclencheurs** : Import automatique, date VA importée = date proposition
**Détail** : Un utilisateur effectue un import, dans cet import il y a une ligne qui correspond exactement à la date de la valeur et la même valeur que la `PROPOSITION_VALEUR_EN_COURS` associé à l'indicateur et au territoire. 

#### **Étape 10 - Import sur proposition - VA plus récente**
**Description** : Import automatique avec date plus récente que la proposition
**Événements possibles** : `PROPOSITION_VALEUR_IGNOREE_VALEUR_HISTORISEE`, `VALEUR_HISTORISEE`, `VALEUR_CREE`
**Déclencheurs** : Import automatique, date VA importée > date proposition
**Détail** : Un utilisateur effectue un import, dans cet import il y a une ligne qui correspond à une date plus récente que la date de la `PROPOSITION_VALEUR_EN_COURS` associé à l'indicateur et au territoire. La proposition est donc ignorée, l'ancienne valeur reçoit un évenement de `VALEUR_HISTORISEE` et un évenement de `VALEUR_CREE` pour la nouvelle valeur. Le `VALEUR_CREE` recoupe avec l'évenement 1.

#### **Étape 11 - Import hors proposition - même date de VA**
**Description** : Import automatique sans proposition en cours, même date
**Événements possibles** : `VALEUR_MODIFIEE`
**Déclencheurs** : Import automatique, pas de proposition active
**Détail** : L'utilisateur effectue un import, dans cet import il y a une ligne qui correspond à la même date de valeur qu'une valeur existante, on met donc un évenement de `VALEUR_MODIFIEE` pour la valeur existante, à condition que la valeur importée soit différente de la dernière valeur existante.


#### **Étape 12 - Import sur proposition - VA plus récente (bis)**
**Description** : Second cas d'import avec valeur plus récente
**Événements possibles** : `VALEUR_HISTORISEE`, `VALEUR_CREE`
**Déclencheurs** : Import automatique, date VA importée > toute proposition
**Détail** : L'utilisateur effectue un import, dans cet import il y a une ligne qui correspond à une date plus récente que la date de la valeur existante associé à l'indicateur et au territoire. La valeur existante reçoit un évenement de `VALEUR_HISTORISEE` et un évenement de `VALEUR_CREE` pour la nouvelle valeur. On ne pourra pas voir dans l'historique les 2 valeurs. Le `VALEUR_CREE` recoupe avec l'évenement 1.
